Trois articles durant, on a pris Front Matter tel qu'il sort de la boîte : installé, configuré finement, utilisé au quotidien. Rien qu'on n'ait ajouté à l'outil lui-même.

Cet article change de registre. On va **étendre** Front Matter : lui apprendre à pré-remplir des articles, à insérer des blocs tout faits, à exposer nos propres boutons dans le panneau, et à ranger sa configuration dans plusieurs fichiers plutôt qu'un seul `frontmatter.json` de 450 lignes. C'est le moment où l'extension cesse d'être un formulaire et devient une partie de l'outillage du dépôt.

:::

## Les templates : ne plus partir d'une page blanche
<Columns className="text--justify">
<Column>
Dans [l'article 2](/blog/install-front-matter-cms-docusaurus/), **Create content** générait un article vide — juste le frontmatter déduit du content type, et un corps désespérément blanc. À chaque nouvel article, je recollais donc les mêmes éléments : le bloc de badges, le `<div className="text--justify">`, le `{/* truncate */}`. Copié depuis le dernier article, à chaque fois.

Un **template** supprime ce geste. C'est un fichier Markdown complet — frontmatter **et** corps — que Front Matter recopie à la création.

Premier point pratique : à l'initialisation, Front Matter **ne crée pas** le dossier `.frontmatter/templates/`. Si vous préférez partir de zéro, lancez d'abord `Front Matter: Initialize the template folder`, ou créez le dossier à la main.

Le plus simple, cependant, est de partir d'un article existant qui vous plaît, puis de cliquer sur **Create template**, dans la section **Other actions** du panneau, avec l'article ouvert — l'action crée le dossier au passage et y dépose le fichier.
</Column>
<Column className="margin-vert--lg">
![Le bouton Create template dans la section Other actions du panneau](/img/frontmattercms/post4/create-template.png)
Le bouton peut apparaître grisé selon le fichier au premier plan : ouvrez l'article que vous voulez transformer en template avant de cliquer. La même action existe à la palette de commandes, si vous préférez le clavier :

<Terminal title="VS Code — palette de commandes">

Front Matter: Create a template from the current file

</Terminal>
</Column>
</Columns>

Le fichier atterrit dans `.frontmatter/templates/`, aux côtés de la configuration :

<Trees>
  <Folder label=".frontmatter" expanded={true}>
    <Folder label="config" />
    <Folder label="database" />
    <Folder label="templates" expanded={true}>
      <File label="article.md" icon="markdown" />
    </Folder>
  </Folder>
</Trees>

On peut ensuite l'épurer pour ne garder que le squelette réutilisable :

```markdown title=".frontmatter/templates/article.md"
---
title: ""
slug: ""
description: ""
authors:
  - docux
mainTag: ""
date: ""
draft: true
inLanguage: en
series: ""
---

<div>
<center>
[![Developer](https://img.shields.io/badge/Developer-Docux-green.svg)](https://github.com/Juniors017)
</center>
</div>

<div className="text--justify">

{/* truncate */}

</div>
```

Un seul réglage active le mécanisme — la fonctionnalité est éteinte par défaut :

```json title="frontmatter.json"
"frontMatter.templates.enabled": true
```

Inutile de préciser le dossier : `frontMatter.templates.folder` vaut déjà `.frontmatter/templates` par défaut, on ne le déclare que pour ranger les templates ailleurs.

À partir de là, **Create content** propose de choisir un template au lieu de partir de zéro. Le lien peut même être rendu permanent : la propriété `template` posée sur un content type force chaque nouvel article de ce type à démarrer du template désigné.

```json title="frontmatter.json — dans le content type"
{
  "name": "article",
  "template": ".frontmatter/templates/article.md",
  "fields": [ "..." ]
}
```

:::note Template vs content type — ne pas confondre
Le **content type** décrit le *formulaire* (quels champs, quels types). Le **template** fournit le *contenu de départ* (valeurs par défaut **et** corps du fichier). L'un remplit le panneau, l'autre remplit la page. Ils sont complémentaires, pas concurrents.
:::

## Les snippets : vos composants MDX à portée de clic

Un blog Docusaurus, c'est du MDX truffé de composants maison. Sur ce blog, je réutilise sans arrêt `<Columns>`, `<Terminal>`, `<Trees>`… et j'ai la flemme de tout écrire — voire, parfois, je ne me souviens plus de la structure exacte des balises imbriquées, alors que la majorité sont des composants que j'ai moi-même créés. Résultat : je rouvre un ancien article pour copier le motif. Encore du copier-coller.


Les **snippets** (l'icône ciseaux dans l'interface) répondent exactement à ça. Ils se définissent dans `frontMatter.content.snippets`, et — bonne surprise — on en a **déjà un** depuis l'article 2, glissé secrètement pour me faciliter la rédaction.

![L'icône ciseaux du panneau, qui donne accès aux snippets](/img/frontmattercms/post4/snippets.png)

Chaque chaîne de `body` est une ligne ; le bouton **Insert snippet** (ou la vue Snippets du dashboard) colle le bloc au curseur. Tel quel, c'est du texte fixe — pratique, mais un snippet donne sa pleine mesure dès qu'on lui ajoute des **champs**.

```json title="frontmatter.json"
"frontMatter.content.snippets": {
  "Columns": {
    "description": "",
    "body": [
      "<Columns>",
      "<Column>",
      "",
      "</Column>",
      "<Column>",
      "</Column>",
      "</Columns>"
    ],
    "fields": []
  }
}
```



Reprenons donc ce même `<Columns>` et poussons-le jusqu'au bout : **largeur, marge, padding et contenu, réglables de chaque côté**. Huit champs, et plus une seule classe à se rappeler.

```json title="frontmatter.json — version complète"
"Columns": {
  "description": "Deux colonnes — largeur, marge et padding réglables de chaque côté",
  "body": [
    "<Columns>",
    "<Column className=\"[[leftWidth]] [[leftMargin]] [[leftPadding]]\">",
    "[[&leftContent]]",
    "</Column>",
    "<Column className=\"[[rightWidth]] [[rightMargin]] [[rightPadding]]\">",
    "[[&rightContent]]",
    "</Column>",
    "</Columns>"
  ],
  "fields": [
    { "name": "leftWidth", "title": "Gauche — largeur", "type": "choice", "choices": ["col--6", "col--8", "col--4", "col--3", "col--9"], "default": "col--6" },
    { "name": "leftMargin", "title": "Gauche — marge", "type": "choice", "choices": ["margin--none", "margin--sm", "margin--md", "margin--lg", "margin-vert--md"], "default": "margin--none" },
    { "name": "leftPadding", "title": "Gauche — padding", "type": "choice", "choices": ["padding--none", "padding--sm", "padding--md", "padding--lg"], "default": "padding--none" },
    { "name": "leftContent", "title": "Gauche — contenu", "type": "string", "default": "FM_SELECTED_TEXT" },
    { "name": "rightWidth", "title": "Droite — largeur", "type": "choice", "choices": ["col--6", "col--4", "col--8", "col--9", "col--3"], "default": "col--6" },
    { "name": "rightMargin", "title": "Droite — marge", "type": "choice", "choices": ["margin--none", "margin--sm", "margin--md", "margin--lg", "margin-vert--md"], "default": "margin--none" },
    { "name": "rightPadding", "title": "Droite — padding", "type": "choice", "choices": ["padding--none", "padding--sm", "padding--md", "padding--lg"], "default": "padding--none" },
    { "name": "rightContent", "title": "Droite — contenu", "type": "string" }
  ]
}
```

Trois idées se lisent dans ce bloc :

- **Les placeholders** reçoivent les valeurs saisies, et rien n'empêche d'en concaténer plusieurs dans un même attribut : `className="[[leftWidth]] [[leftMargin]] [[leftPadding]]"` compose la classe finale à partir de trois menus. Les délimiteurs `[[ ]]` sont d'ailleurs réglables (`openingTags` / `closingTags`).
- **Un champ `choice`** impose une liste fermée — ici les classes de grille et d'espacement d'Infima, que notre composant `<Column>` transmet tel quel. Fini le `col--7` tapé de travers : on choisit dans une liste. Les variantes `--none` servent d'option « rien », pour ne pas laisser de classe vide.
- **`FM_SELECTED_TEXT`** est la valeur magique : un champ qui l'a pour défaut se pré-remplit avec le **texte sélectionné**, et le placeholder du corps de même `name` le reçoit. Sélectionnez un paragraphe, insérez le snippet, choisissez `col--8` puis `col--4` : votre texte remplit une large colonne de gauche, une étroite l'attend à droite.
- **L'esperluette devant le nom** — `[[&leftContent]]` et non `[[leftContent]]` — n'est pas décorative, et c'est le sujet du prochain encadré.

:::caution Mettez une esperluette dès qu'il y a du texte libre
Front Matter **échappe en entités HTML** tout ce qu'un placeholder insère. Mon premier `Columns` écrivait `[[leftContent]]` : j'ai sélectionné un paragraphe de cet article même, inséré le snippet, et récupéré ceci dans mon MDX —

```text
Un blog Docusaurus, c&#39;est du MDX truffé de composants maison…
&#x60;&lt;Columns&gt;&#x60;, &#x60;&lt;Terminal&gt;&#x60;…
```

Chaque apostrophe, chaque backtick, chaque chevron transformé. Le paragraphe s'affichait tel quel sur la page, entités comprises.

Le préfixe `&` réclame la valeur brute : `[[&leftContent]]`. À poser sur **tout placeholder qui transporte du texte libre, un chemin ou du balisage** — en pratique, tous vos champs `string`. Les champs `choice` qui ne servent qu'à des noms de classes n'en ont pas besoin.
:::

Une limite quand même : la sélection est **unique**, elle n'alimente qu'un seul champ. Le contenu de droite reste donc à saisir — et pour du code ou une image, mieux vaut laisser le champ vide et écrire directement dans l'éditeur, où l'on est plus à l'aise pour rédiger.

Mettons tout ça ensemble. Voici le snippet que j'aurais dû écrire dès le début de la série : il **enveloppe le texte sélectionné dans une admonition**, dont le type se choisit dans une liste — y compris le `:::docu` maison de ce blog. Un champ `choice` pour le type, un champ libre pour le titre, et la sélection récupérée automatiquement :

```json title="frontmatter.json"
"Admonition": {
  "description": "Envelopper la sélection dans une admonition",
  "body": ["\n:::[[type]] [[&title]]", "[[&selection]]", ":::\n"],
  "fields": [
    {
      "name": "type",
      "title": "Type d'encadré",
      "type": "choice",
      "choices": ["tip", "info", "caution", "danger", "note", "docu"],
      "default": "tip"
    },
    { "name": "title", "title": "Titre (optionnel)", "type": "string" },
    { "name": "selection", "title": "Contenu", "type": "string", "default": "FM_SELECTED_TEXT" }
  ]
}
```

Le geste devient : je sélectionne un paragraphe déjà écrit, je lance le snippet, je choisis _caution_ dans la liste, je tape un titre — et mon paragraphe se retrouve encadré, sans que j'aie tapé une seule fois `:::`. Trois types de valeurs (liste fermée, texte libre, sélection) dans un seul snippet : c'est là qu'on mesure que l'outil ne se contente pas d'insérer du texte mort.

### Le piège à connaître en MDX : couper le _wrapper_

Si vous ne deviez retenir qu'une chose de cette section, ce serait celle-ci — à régler **avant** d'insérer votre premier snippet. Par défaut, Front Matter entoure chaque snippet inséré de commentaires qui mémorisent son `id` et les valeurs de ses champs, pour pouvoir le **rééditer** plus tard. Votre belle admonition arrive donc emballée ainsi :

```markdown title="ce que le wrapper insère… et qui s'affiche en MDX"
<!-- FM:Snippet:Start data:{"id":"Admonition","fields":[…]} -->

:::tip Astuce
Votre contenu.
:::

<!-- FM:Snippet:End -->
```

Sur un générateur en **Markdown pur**, ces commentaires HTML sont invisibles au rendu — le mécanisme est même astucieux. Mais Docusaurus **dans mon contexte** lit du **MDX**, où `<!-- -->` n'est pas un commentaire valide : les deux lignes `FM:Snippet` **s'affichent telles quelles sur la page publiée**. J'y suis tombé en testant les snippets de cet article.

La parade tient en une ligne :

```json title="frontmatter.json"
"frontMatter.snippets.wrapper.enabled": false
```

Le seul prix : Front Matter ne saura plus retrouver un snippet déjà inséré pour le modifier en place. Sur ce blog, où un snippet sert de tremplin puis vit sa vie en MDX, c'est un échange gagnant.

### Les snippets pour vos médias

En créant un snippet depuis le dashboard, une option intrigue : **« Is a media snippet? »**, décrite par _« Use the current snippet for inserting media files into your content »_. C'est le champ `isMediaSnippet` du JSON. Cochée, elle change complètement le point d'entrée du snippet : au lieu d'apparaître dans l'éditeur pour envelopper du texte, le snippet **s'attache aux cartes de la médiathèque** — on l'applique à une image plutôt qu'à une sélection.

Ses placeholders ne sont donc plus les vôtres, mais ceux fournis par le média : `mediaUrl`, `alt`, `caption`, `filename`, `title`, `mediaWidth`, `mediaHeight`. De quoi brancher directement notre lightbox maison, `<ImageOnClick>`, sur une image de la médiathèque — sans jamais recopier un chemin à la main :

```json title="frontmatter.json"
"Lightbox": {
  "description": "Depuis une carte média : insère l'image dans la lightbox ImageOnClick",
  "isMediaSnippet": true,
  "body": [
    "<ImageOnClick imageUrl=\"[[&mediaUrl]]\" altText=\"[[&alt]]\" buttonName=\"[[&buttonName]]\" />"
  ],
  "fields": [
    { "name": "altText", "title": "Texte alternatif", "type": "string" },
    { "name": "buttonName", "title": "Libellé du lien", "type": "string", "default": "Voir l'image" }
  ]
}
```

Ici encore, **l'esperluette est indispensable** : sans elle, `[[mediaUrl]]` produit un chemin inutilisable, chaque `/` transformé en `&#x2F;`.

```jsx
<ImageOnClick imageUrl="&#x2F;img&#x2F;post3&#x2F;menucard.png" />
```

Autre détail à connaître : **les champs média ne remplissent que ce qui existe**. `alt` et `caption` puisent dans les métadonnées de l'image (`mediaDb.json`) — le mien étant vide, ils arrivent vides. D'où le `buttonName` déclaré ici comme **champ à saisir**, avec un défaut. Seul `mediaUrl` est toujours automatique : c'est de toute façon le seul qu'on ne veut jamais taper.

Le vrai déclic vient quand on comprend qu'un media snippet n'est pas limité à une balise : **son corps peut être une mise en page entière**. Le motif que j'utilise sans arrêt dans cette série — une capture d'un côté, du texte ou du code de l'autre — devient alors un seul clic depuis la carte de l'image :

```json title="frontmatter.json"
"Image + colonnes": {
  "description": "Depuis une carte média : insère l'image dans une colonne, texte à droite",
  "isMediaSnippet": true,
  "body": [
    "<Columns>",
    "<Column className=\"[[imageWidth]]\">",
    "<img src=\"[[&mediaUrl]]\" alt=\"[[&altText]]\" />",
    "</Column>",
    "<Column>",
    "",
    "</Column>",
    "</Columns>"
  ],
  "fields": [
    { "name": "imageWidth", "title": "Largeur de la colonne image", "type": "choice", "choices": ["col--6", "col--4", "col--8"], "default": "col--6" },
    { "name": "altText", "title": "Texte alternatif", "type": "string" }
  ]
}
```

:::tip Où est passé mon snippet ? Le mode d'emploi
Premier réflexe après l'avoir déclaré : ouvrir un article, chercher **Insert snippet**… et ne rien trouver. C'est normal, et la documentation est formelle : _« You cannot insert media snippets into your content like you can with content snippets. Instead, you will find them on the media cards. »_ Un media snippet vit **sur les cartes de la médiathèque**, jamais dans la liste de l'éditeur.

Le geste, dans l'ordre :

1. **Ouvrez l'article** et placez le curseur là où l'image doit atterrir.
2. Passez au **dashboard → onglet Media**.
3. Sur la **carte de l'image** voulue, déclenchez le snippet.
4. Renseignez vos champs — ici la largeur de colonne.

La structure à deux colonnes s'insère alors au curseur de l'article resté ouvert, **image en place, chemin jamais tapé**. Il ne reste qu'à écrire à droite.
:::

Notez que `mediaUrl` et `alt` ne sont pas déclarés dans `fields` : ils viennent du média lui-même. L'`alt` puise dans les métadonnées de l'image (`mediaDb.json`) — si, comme moi, vous ne les remplissez pas, il arrivera vide et restera à compléter à la main. Une bonne raison de s'y mettre.

:::note Créer des snippets ≠ les utiliser
Ces deux capacités sont séparées, et c'est précisément à quoi servent les deux _features_ de la section modes : `dashboard.snippets.view` **utilise** les snippets (les insérer), `dashboard.snippets.manage` permet de les **créer et éditer**. Un mode qui garde `view` sans `manage` — comme notre mode `minimal` plus haut — laisse toute l'équipe insérer les snippets validés, mais **empêche d'en créer de nouveaux à la volée**. La bibliothèque reste maîtrisée, versionnée dans `frontmatter.json`.
:::

## Les actions sur mesure : vos boutons dans le panneau

C'est l'extension la plus puissante, et la moins connue. Front Matter permet d'ajouter **vos propres boutons** dans le panneau, chacun exécutant un script Node, via le paquet `@frontmatter/extensibility` :

```bash
npm i -D @frontmatter/extensibility
```

Un script reçoit son contexte de `ContentScript.getArguments()` — `filePath` (le fichier ouvert), `workspacePath` (la racine du projet), le `frontMatter` déjà parsé, et les `answers` d'éventuelles questions posées à l'utilisateur. Il rend la main avec `ContentScript.done()`, dont le message s'affiche dans le panneau. La déclaration du bouton tient en quatre clés :

```json title="frontmatter.json"
"frontMatter.custom.scripts": [
  {
    "title": "Vider le cache Docusaurus",
    "script": "./scripts/clear-cache.mjs",
    "command": "node",
    "output": "notification"
  }
]
```

Les propriétés utiles : `output` vaut `editor` ou `notification` selon qu'on veut réinjecter du texte ou juste afficher un message ; `type` (`content`, `mediaFolder`, `mediaFile`) décide où le bouton apparaît ; `bulk` autorise l'exécution sur plusieurs fichiers d'un coup.

Avant d'aller plus loin, un garde-fou : **ne réinventez pas ce que Front Matter fait déjà.** Exemple : le panneau SEO compte les mots de l'article — `frontMatter.taxonomy.seoContentLengh` permet même de fixer la longueur visée — ainsi que les caractères du titre et de la description. L'extension valide aussi le frontmatter contre le content type, et son panneau _Content Health_ mesure la lisibilité, repère les liens morts et signale les articles qui vieillissent. Elle sait même vider son propre cache.

Une action maison n'a donc de valeur que pour ce que l'extension **ne peut pas** connaître : votre outillage, vos services, vos conventions.

**Exemples rapides à mettre en place.** Quelques lignes suffisent pour rapatrier dans le panneau les commandes qu'on tape sans arrêt au terminal :

- **Vider le cache Docusaurus** — le fameux `npm run clear`, réflexe obligatoire après avoir ajouté un article ou touché à un plugin. Le script l'exécute dans le dossier du projet et renvoie une notification.
- **Vider le cache npm** — `npm cache clean --force`, pour le jour où une dépendance refuse de s'installer proprement.
- **Copier l'URL de production** — reconstruire `https://votre-site/blog/<slug>/` à partir du frontmatter, pour la coller ailleurs sans la retaper.
- **Vérifier les textes alternatifs** — une regex sur le corps qui compte les images sans `alt`. Content Health ne couvre pas ce point, et c'est une convention à laquelle je tiens.

**Plus ambitieux, pour un week-end tranquille.** Là, on branche des services externes — et on sort définitivement du périmètre de l'extension :

- **Rédiger le post BlueSky.** À chaque publication, j'écris à la main une accroche de 300 caractères qui pointe vers l'article. Un script part du `title` et de la `description`, assemble le texte et vérifie la limite.
- **Publier sur BlueSky, puis réinjecter le `blueSkyRecordKey`.** Le prolongement logique : poster via l'API, récupérer l'identifiant du post et l'écrire dans le frontmatter (`output: "editor"`). C'est précisément le geste manuel qui clôt chaque article de cette série.
- **Fabriquer la carte sociale.** Générer l'image Open Graph — titre incrusté sur un gabarit — avec le même `sharp` que [le plugin d'images du blog](/blog/image-optimizer-docusaurus-plugin/), l'enregistrer dans `static/`, et poser le champ `image`.


Aucune de ces idées n'existe dans l'extension, et les dernières ne peuvent pas y exister : elles parlent à _votre_ hébergeur social, _votre_ chaîne d'images, _votre_ organisation bilingue. L'extension fournit le bouton ; vous fournissez le métier.

### Un espace « Maintenance » dans le panneau

Les deux premières idées de la liste accessible sont maintenant dans ma configuration, avec un test de build, regroupées sous un même préfixe :
<Columns>
<Column className="col--8 margin--none padding--none">
```json title="frontmatter.json"
"frontMatter.custom.scripts": [
  { "id": "maintenance-build", "title": "Maintenance · Tester le build", "script": "./scripts/test-build.mjs", "command": "node", "output": "notification" },
  { "id": "maintenance-cache-docusaurus", "title": "Maintenance · Vider le cache Docusaurus", "script": "./scripts/clear-cache.mjs", "command": "node", "output": "notification" },
  { "id": "maintenance-cache-npm", "title": "Maintenance · Vider le cache npm", "script": "./scripts/clear-npm-cache.mjs", "command": "node", "output": "notification" }
]
```

:::note Pas de vraies catégories — un préfixe suffit
Le schéma d'une action expose `id`, `title`, `script`, `command`, `output`, `outputType`, `type`, `bulk`, `hidden`, `nodeBin`, `environments` et `contentTypes` — mais **aucune notion de groupe**. Le préfixe `Maintenance · ` dans le `title` est donc une simple convention de nommage : les boutons se rangent visuellement les uns sous les autres, sans que l'extension n'en sache rien. Efficace, et gratuit.
:::
</Column>

Vider le cache Docusaurus tient en trois lignes utiles — le geste qu'on répète après chaque ajout d'article :

<Snippet source="scripts/clear-cache.mjs"   filename="scripts/clear-cache.mjs" />

Le `workspacePath` livré par `getArguments()` sert de répertoire de travail : le script s'exécute à la racine du projet, quel que soit le fichier ouvert. Le `try/catch` renvoie l'erreur en notification plutôt que d'échouer en silence. Le jumeau pour npm est identique, à la commande près.

:::caution N'appelez pas `npm` depuis le script
Ma première version faisait un `execSync("npm run clear")`. Au terminal, impeccable ; depuis le bouton, échec sec :

<Terminal title="Terminal">
Command failed: node "…\scripts\test-build.mjs"
La syntaxe du nom de fichier, de répertoire ou de volume est incorrecte.
</Terminal>

La raison : `execSync` passe par un shell — `cmd.exe` sous Windows — et le script n'est pas lancé depuis un terminal mais par l'extension, avec un environnement réduit où `npm` n'est plus résolu de la même façon.

La parade est plus robuste **et** plus rapide : appeler le binaire directement avec le node courant, sans shell du tout. `execFileSync` au lieu de `execSync`, `process.execPath` pour node, et le chemin du binaire reconstruit depuis `workspacePath`. Plus de PATH, plus de `cmd.exe`, plus de guillemets à échapper. Même logique pour npm, dont l'entrée JS se trouve à côté de l'exécutable node (`node_modules/npm/bin/npm-cli.js`).
:::

Le bouton de test de build va un cran plus loin : il lance la compilation complète et répond **OK** ou **KO**, en comptant au passage les avertissements — la règle des zéro warning de ce blog devient vérifiable d'un clic.

<Snippet source="scripts/test-build.mjs" filename="scripts/test-build.mjs" />


:::caution Un bouton qui prend deux minutes
Un build Docusaurus complet n'est pas instantané. Pendant l'exécution, la notification se fait attendre et rien ne l'indique clairement : c'est le prix d'une vérification sérieuse. À réserver au moment de publier, pas à chaque sauvegarde.
:::

Manque un quatrième bouton à cet ensemble : vider le cache de Front Matter lui-même. Il n'existera pas, et pour une raison instructive — **une action custom est un script Node, exécuté hors de VS Code**. Elle peut lancer une commande système, lire et écrire des fichiers du projet… mais pas déclencher une commande de l'éditeur. Or ce cache-là ne vit pas dans le dépôt, mais dans le stockage de l'extension.

La bonne réponse n'est donc pas un bouton, c'est un **raccourci clavier** — plus rapide encore. La commande s'appelle `frontMatter.cache.clear` ; il suffit de la lier dans `keybindings.json` :

```json title="keybindings.json (VS Code)"
{
  "key": "ctrl+alt+c",
  "command": "frontMatter.cache.clear"
}
```

C'est un réflexe qui vaut pour toutes les commandes de l'extension : ce que le panneau n'expose pas en bouton, la palette le connaît — et tout ce que la palette connaît peut recevoir un raccourci.

:::caution Un script, pas un jouet
Ces scripts s'exécutent avec Node sur votre machine, avec vos droits. C'est un atout — accès disque, réseau, `node_modules` — mais un script partagé dans un dépôt public s'exécute chez qui clone le projet. À traiter avec la même prudence qu'un hook Git ou un script npm.
:::

## Des modes : un panneau qui s'adapte à ce que vous faites

À force d'ajouter templates, snippets et boutons, le panneau se remplit. Or, selon le moment, on n'a pas besoin de tout : quand j'**écris**, je veux le formulaire, les compteurs SEO et les boutons de publication — pas la gestion des taxonomies ni les actions Git. Quand je fais du **ménage** (comme les fusions de tags de l'article précédent), c'est l'inverse.

Les **modes** répondent exactement à ça. Un mode porte un `id` et une liste de `features` — les seules parties de l'interface qui resteront visibles. On les déclare dans `frontMatter.global.modes`, et un sélecteur dans la **barre d'état** (en bas de la fenêtre) bascule de l'un à l'autre en un clic.

Voici deux modes cohérents pour ce blog — un pour écrire, un pour tout maintenir :

```json title="frontmatter.json"
"frontMatter.global.modes": [
  {
    "id": "minimal",
    "features": [
      "panel.contentType",
      "panel.metadata",
      "panel.seo",
      "panel.actions",
      "panel.otherActions",
      "dashboard.snippets.view"
    ]
  },
  {
    "id": "complete",
    "features": [
      "panel.globalSettings",
      "panel.contentType",
      "panel.metadata",
      "panel.seo",
      "panel.actions",
      "panel.gitActions",
      "panel.recentlyModified",
      "panel.otherActions",
      "dashboard.snippets.view",
      "dashboard.snippets.manage",
      "dashboard.data.view",
      "dashboard.taxonomy.view"
    ]
  }
],
"frontMatter.global.activeMode": "complete"
```

La logique est simple : **`minimal`** ne garde que ce qu'on touche en rédigeant — le formulaire (`panel.contentType`), les métadonnées comme le statut brouillon (`panel.metadata`), les compteurs SEO (`panel.seo`), les actions de publication (`panel.actions` et `panel.otherActions`) et l'insertion de snippets (`dashboard.snippets.view`). **`complete`** rallume tout : les réglages globaux, les actions Git, les récemment modifiés, et surtout les surfaces de gestion du dashboard — gestion des snippets, fichiers de données et **taxonomie** (là où se font les fusions de tags).




Les douze `features` disponibles couvrent huit sections du panneau (`panel.globalSettings`, `panel.seo`, `panel.actions`, `panel.metadata`, `panel.contentType`, `panel.gitActions`, `panel.recentlyModified`, `panel.otherActions`) et quatre vues du dashboard (`dashboard.snippets.view`, `dashboard.snippets.manage`, `dashboard.data.view`, `dashboard.taxonomy.view`). Libre à vous d'inventer un troisième mode `review`, `seo`, ou ce que dicte votre flux.
![Le sélecteur de mode dans la barre d'état de VS Code](/img/frontmattercms/post4/mode.png)

![La liste des modes proposée au clic sur le sélecteur](/img/frontmattercms/post4/selectmode.png)
:::tip Réglage plus fin, action par action
Les modes raisonnent par **sections**. Pour masquer un **bouton précis** sans toucher au reste, `frontMatter.panel.actions.disabled` accepte les identifiants d'actions (`openDashboard`, `createContent`, `optimizeSlug`, `preview`, `openOnWebsite`, `startStopServer`, `customActions`). Les deux se combinent.
:::

:::tip Pas de bouton ? C'est normal
Tant qu'aucun mode n'est déclaré, l'extension n'a rien à proposer : **le sélecteur n'apparaît pas**. Ajoutez les deux modes ci-dessus, rechargez la fenêtre, et il se montre en bas à gauche.
:::

Le partage des rôles est bien pensé, et je l'ai vérifié en basculant : **la définition des modes est versionnée, le mode actif ne l'est pas**. Les modes vivent dans `frontmatter.json` et voyagent donc avec le dépôt — arriver sur le projet, c'est hériter d'un `minimal` et d'un `complete` déjà pensés. Mais quand vous cliquez sur le sélecteur, aucun fichier suivi ne bouge : le choix atterrit dans le stockage local de VS Code (`workspaceStorage`). `frontMatter.global.activeMode` ne fixe que le mode **par défaut**, pour qui ouvre le projet sans avoir jamais choisi.

Le résultat est exactement ce qu'on veut en équipe : une configuration commune, un panneau volontairement épuré pour le flux éditorial validé — et chacun libre de basculer quand il veut, **sans polluer les diffs Git** de ses préférences d'affichage.

## Éclater la configuration : la promesse de l'article 1

Souvenez-vous : dès [le premier article](/blog/why-front-matter-cms-docusaurus/), j'avais promis qu'on reviendrait sur `frontMatter.extends` et le découpage de la config. Le moment est venu — et il tombe particulièrement bien, parce que le besoin est né de ce chapitre même.

En ouvrant cet article, mon `frontmatter.json` faisait **191 lignes**. Puis on y a ajouté les snippets, les actions de maintenance, les modes du panneau :

| Étape                                        | Lignes  |
| -------------------------------------------- | ------- |
| Au début de cet article                      | 191     |
| Après les snippets et le réglage du wrapper  | 249     |
| Après les trois actions de maintenance       | 371     |
| Après le `Columns` à huit champs et la lightbox | 419  |
| Après les deux modes du panneau              | **450** |

Plus du double, pour un seul fichier où retrouver un réglage devenait pénible. Ce n'est donc pas une coquetterie de rangement : c'est le prix de tout ce qu'on vient de construire.

Front Matter offre deux mécanismes pour ranger ça, à ne pas confondre.

### Le découpage par convention de dossiers

Le premier ne demande aucune déclaration : il repose sur une **arborescence attendue** sous `.frontmatter/config/`. Voici celle de ce blog, après découpage :

<Trees>
  <Folder label=".frontmatter" expanded={true}>
    <Folder label="config" expanded={true}>
      <File label="frontmatter.json" icon="json" />
      <Folder label="content" expanded={true}>
        <Folder label="snippets" expanded={true}>
          <File label="Columns.json" icon="json" />
          <File label="Terminal.json" icon="json" />
          <File label="Admonition.json" icon="json" />
          <File label="Lightbox.json" icon="json" />
          <File label="Image + colonnes.json" icon="json" />
        </Folder>
      </Folder>
      <Folder label="taxonomy" expanded={true}>
        <Folder label="contentTypes" expanded={true}>
          <File label="article.json" icon="json" />
        </Folder>
      </Folder>
      <Folder label="custom" expanded={true}>
        <Folder label="scripts" expanded={true}>
          <File label="maintenance-build.json" icon="json" />
          <File label="maintenance-cache-docusaurus.json" icon="json" />
          <File label="maintenance-cache-npm.json" icon="json" />
        </Folder>
      </Folder>
    </Folder>
    <Folder label="templates" />
    <Folder label="database" />
  </Folder>
</Trees>

Chaque fichier contient **une seule entrée** : un snippet, un content type, une action. Le nom du fichier reprend l'identifiant de l'élément — la clé du snippet, l'`id` de l'action, le `name` du content type.

Trois pièges m'ont coûté du temps.

:::caution `contentTypes`, pas `contenttypes`
Le dossier des content types s'écrit en **camelCase** : `.frontmatter/config/taxonomy/contentTypes`. Avec `contenttypes` tout en minuscules, le fichier est ignoré — mon formulaire perdait ses 19 champs sans le moindre message d'erreur. C'est [Elio Struyf](https://discord.gg/JBVtNMsJFB), l'auteur de l'extension, qui m'a donné la bonne casse quand je lui ai posé la question sur le Discord.
:::

:::caution Redémarrez VS Code, pas seulement la config
La commande `Front Matter: Refresh Front Matter Settings` recharge les réglages, et c'est ce qu'il faut après avoir **édité** un fichier de configuration. Mais après en avoir **déplacé** un — a fortiori après avoir déménagé le fichier racine — elle ne suffit pas : il faut **redémarrer VS Code**. Sans ça, on croit à tort que le découpage a échoué, et on part chercher une erreur qui n'existe pas.
:::

:::caution Les chemins relatifs changent de sens
Une action custom déclarée dans le fichier de configuration racine peut pointer son script en relatif :

```json
{ "script": "./scripts/clear-npm-cache.mjs" }
```

Déplacez la même déclaration dans un fichier éclaté, et le bouton apparaît… mais ne fait plus rien. Le chemin ne se résout plus depuis la racine du projet. Le jeton `[[workspace]]` lève l'ambiguïté :

```json
{ "script": "[[workspace]]/scripts/clear-npm-cache.mjs" }
```

À faire systématiquement dès qu'un chemin quitte le fichier principal.
:::

### Le dernier pas : vider la racine

À ce stade, il reste un fichier à la racine du projet — `frontmatter.json`, réduit à ses réglages globaux. On peut s'arrêter là, ou aller au bout : Front Matter cherche sa configuration **aussi** dans `.frontmatter/config`. Rien n'empêche donc d'y déplacer ce dernier fichier, sous le même nom.

<Trees>
  <Folder label="mon-projet" expanded={true}>
    <Folder label=".frontmatter" expanded={true}>
      <Folder label="config" expanded={true}>
        <File label="frontmatter.json" icon="json" />
      </Folder>
    </Folder>
    <Folder label="blog" />
    <Folder label="src" />
    <Folder label="static" />
  </Folder>
</Trees>

La racine du projet ne porte plus aucune trace de l'extension, et le dossier `.frontmatter/` contient l'intégralité du paramétrage : réglages, content type, snippets, actions, templates et bases de données.

Le bilan de l'opération, sur ce blog :

| | Avant | Après |
| --- | --- | --- |
| Fichier de config à la racine | 450 lignes | **aucun** |
| Réglages globaux | mêlés au reste | `.frontmatter/config/frontmatter.json`, 79 lignes |
| Content type | dans le même fichier | son fichier dédié |
| Snippets | dans le même fichier | 5 fichiers |
| Actions custom | dans le même fichier | 3 fichiers |


### `frontMatter.extends` : la liste explicite

Le second mécanisme ne devine rien : `frontMatter.extends` énumère les fichiers de configuration à charger. C'est **l'approche que préfère l'auteur de l'extension**, et on comprend pourquoi — un fichier par domaine, tout est visible d'un coup d'œil :

```json title="frontmatter.json"
"frontMatter.extends": [
  ".frontmatter/configuration/contenttypes.json",
  ".frontmatter/configuration/snippets.json",
  ".frontmatter/configuration/scripts.json",
  ".frontmatter/configuration/pagefolders.json"
]
```

Plus de convention à respecter, plus de casse à deviner : vous nommez vos fichiers comme vous voulez, du moment qu'ils sont listés. Pour un projet qui grossit, c'est plus prévisible que l'arborescence implicite.

Et surtout, `extends` accepte aussi des **URL** :

```json title="frontmatter.json"
"frontMatter.extends": [
  "https://exemple.com/frontmatter/preset.json",
  ".frontmatter/configuration/local.json"
]
```

C'est ce qui ouvre le travail à plusieurs projets : une équipe publie un preset commun — content types, snippets, conventions — hébergé où elle veut, y compris dans un dépôt Git servi en brut. Chaque site l'étend et garde son `frontmatter.json` local pour ses spécificités.

:::note Qui gagne en cas de conflit ?
L'ordre de priorité est sans ambiguïté : le `frontmatter.json` local **écrase** le découpage `.frontmatter/config/`, qui lui-même **écrase** les configurations importées via `extends`. Votre fichier local a toujours le dernier mot — une base partagée ne peut jamais vous imposer un réglage que vous redéfinissez chez vous.
:::

### Vérifier que tout est bien recomposé

Une configuration éclatée pose une question légitime : **comment savoir ce que l'extension a réellement chargé ?** Front Matter répond avec une commande peu connue, et c'est le meilleur compagnon de ce chapitre :

<Terminal title="VS Code — palette de commandes">

Front Matter: Diagnostic logging

</Terminal>

Elle ouvre un document Markdown virtuel — rien n'est écrit sur le disque — qui dresse l'état des lieux :

- les **dossiers de contenu** déclarés, avec leur titre et leur chemin complet ;
- le chemin du **workspace** tel que l'extension le voit ;
- le **nombre total de fichiers**, et le détail des fichiers découverts par type, avec les motifs de recherche employés ;
- surtout : **la configuration complète, entièrement recomposée** — c'est-à-dire le résultat de la fusion de tous vos fichiers éclatés.

C'est ce dernier point qui rend la commande précieuse ici. Après avoir dispersé sa configuration en dix fichiers, on n'a plus aucune vue d'ensemble ; ce rapport la reconstitue. Un content type absent, un snippet qui ne remonte pas, un dossier mal nommé — tout se voit immédiatement, sans deviner.

C'est aussi le premier réflexe à avoir avant de demander de l'aide : le rapport contient exactement ce qu'un mainteneur vous demandera.

C'est exactement le fondement du chapitre suivant : une configuration partageable est le prérequis du travail en équipe.




On a poussé Front Matter très loin dans une logique solo : pré-remplissage, insertion, boutons maison, configuration modulaire. Tout ce qu'on a construit tient sur une machine, un dépôt, un auteur.

Reste la question qu'on a soigneusement évitée jusqu'ici : et à plusieurs ? Dans le prochain article, on ouvre le blog à une équipe — et on verra que Front Matter, dépourvu de comptes et de rôles, s'en remet entièrement à Git pour gérer qui écrit quoi.
